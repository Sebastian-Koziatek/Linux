# iptables – składnia i scenariusz

> **W tej lekcji:** nauczysz się czytać i pisać reguły iptables, a potem zbudujesz od zera kompletną zaporę dla serwera WWW — w kolejności, która nie odetnie Ci dostępu po SSH.

Ta lekcja przekłada teorię z poprzedniej na praktykę: przechodzi przez składnię polecenia `iptables` i najczęstszy scenariusz z życia — świeży serwer WWW, który ma wpuszczać świat na stronę, administratora po SSH i nic więcej.

## Jak to działa

Ogólny kształt polecenia:

```bash
sudo iptables [-t tabela] AKCJA ŁAŃCUCH [dopasowania] -j CEL
```

Akcje na łańcuchu:

| Opcja | Co robi |
|---|---|
| `-L -n -v --line-numbers` | listuje reguły: bez tłumaczenia adresów, z licznikami i numerami |
| `-A INPUT` | dopisuje regułę **na końcu** łańcucha (append) |
| `-I INPUT 1` | wstawia regułę **na pozycji** (insert); bez numeru — na górze |
| `-D INPUT 3` | usuwa regułę numer 3 |
| `-F` | czyści wszystkie reguły łańcucha/tabeli (flush) |
| `-P INPUT DROP` | ustawia politykę domyślną łańcucha |

Dopasowania, czyli „które pakiety”:

| Opcja | Znaczenie | Przykład |
|---|---|---|
| `-p` | protokół | `-p tcp`, `-p udp`, `-p icmp` |
| `-s` | adres/sieć źródłowa | `-s 192.168.10.0/24` |
| `-d` | adres docelowy | `-d 192.168.10.5` |
| `--dport` | port docelowy (wymaga `-p`) | `-p tcp --dport 22` |
| `-i` | karta, którą pakiet wszedł | `-i enp1s0` |
| `-m state --state` | stan połączenia | `--state ESTABLISHED,RELATED` |

`-j` wskazuje cel: `ACCEPT`, `DROP`, `REJECT` lub `LOG`.

## W praktyce

### Scenariusz: zapora serwera WWW

Cel: wpuścić SSH (22), HTTP (80) i HTTPS (443), odrzucić resztę. Pracujemy zdalnie przez SSH, więc **kolejność poleceń ma znaczenie** — polityka DROP wchodzi na końcu, gdy wyjątki już stoją.

```bash
# 1. ruch lokalny (localhost) musi chodzić zawsze - korzysta z niego mnóstwo usług
sudo iptables -A INPUT -i lo -j ACCEPT

# 2. odpowiedzi na połączenia, które już trwają (w tym NASZA sesja SSH)
sudo iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# 3. NAJPIERW zezwalamy na nowe połączenia SSH - zanim cokolwiek zablokujemy!
sudo iptables -A INPUT -p tcp --dport 22 -m state --state NEW -j ACCEPT

# 4. strona WWW: HTTP i HTTPS z całego świata
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# 5. dopiero teraz: wszystko inne odpada
sudo iptables -P INPUT DROP

# serwer nie jest routerem, więc ruch przekazywany też blokujemy
sudo iptables -P FORWARD DROP
```

Kontrola:

Gdy pomylisz kolejność i reguła ogólna zasłoni wyjątek, usuń ją po numerze i wstaw wyżej:

```bash
# usuwamy regułę nr 5 i wstawiamy ją na samą górę łańcucha
sudo iptables -D INPUT 5
sudo iptables -I INPUT 1 -p tcp --dport 443 -j ACCEPT
```

### Zapis reguł na stałe

Reguły iptables żyją **tylko w pamięci** — restart serwera je kasuje. Zapis i odczyt:

```bash
# zrzut bieżących reguł do pliku
sudo iptables-save | sudo tee /etc/sysconfig/iptables

# wczytanie reguł z pliku
sudo iptables-restore < /etc/sysconfig/iptables
```

Żeby reguły wstawały same przy starcie systemu, na RHEL 9/10 służy do tego pakiet **iptables-services** (usługa `iptables.service` czyta właśnie `/etc/sysconfig/iptables`). Zanim ją włączysz, wyłącz firewalld — dwie zapory naraz to prosta droga do chaosu:

```bash
sudo dnf install iptables-services
sudo systemctl disable --now firewalld
sudo systemctl enable --now iptables
```

> **Ważne:** na RHEL 9/10 domyślną i zalecaną zaporą jest **firewalld**, a `iptables` to nakładka na nftables oznaczona jako przestarzała. Powyższą zamianę rób tylko wtedy, gdy naprawdę potrzebujesz czystego iptables — na co dzień te same efekty osiągniesz w firewalld (następna lekcja).

## Najczęstsze błędy i pułapki

- **Polityka DROP przed regułą dla SSH.** Klasyka odcinania samego siebie. Zawsze: najpierw `ACCEPT` dla SSH i `ESTABLISHED`, polityka DROP na końcu. Przy pracy na zdalnym serwerze miej otwartą drugą sesję SSH jako koło ratunkowe.
- **Brak reguły dla `lo`.** Po ustawieniu polityki DROP bez przepuszczenia pętli lokalnej dziwnie psują się rzeczy pozornie niezwiązane z siecią (lokalne bazy, resolver DNS).
- **Reguły zniknęły po restarcie.** Bo żyją w pamięci. `iptables-save` + pakiet iptables-services albo od razu firewalld z opcją `--permanent`.
- **`--dport` bez `-p`.** Port docelowy ma sens tylko dla konkretnego protokołu — bez `-p tcp`/`-p udp` polecenie zwróci błąd.
- **Testowanie zdalnie bez planu B.** Przed eksperymentami na produkcji: `sudo cp` zrzutu reguł, a najlepiej zaplanowany powrót, np. `echo 'iptables -F; iptables -P INPUT ACCEPT' | sudo at now + 10 minutes` — jeśli się zablokujesz, za 10 minut zapora sama się wyczyści.

## Podsumowanie

- Reguła = łańcuch + dopasowania (`-p`, `-s`, `--dport`, `-m state`) + cel (`-j`).
- `-A` dopisuje na końcu, `-I` wstawia na górze, `-D` usuwa po numerze z `--line-numbers`.
- Bezpieczna kolejność budowy zapory: `lo` → `ESTABLISHED` → **SSH** → usługi → polityka DROP.
- Reguły są ulotne: utrwala je `iptables-save` + iptables-services.
- Na RHEL 9/10 to wszystko dzieje się naprawdę w nftables, a domyślną zaporą jest firewalld.

| Polecenie | Co robi |
|---|---|
| `iptables -A INPUT -p tcp --dport 80 -j ACCEPT` | wpuszcza HTTP |
| `iptables -I INPUT 1 -s 192.168.10.7 -j ACCEPT` | wyjątek na górze listy |
| `iptables -D INPUT 3` | usuwa regułę nr 3 |
| `iptables -P INPUT DROP` | polityka domyślna: odrzucaj |
| `iptables-save` / `iptables-restore` | zapis / odczyt reguł |
